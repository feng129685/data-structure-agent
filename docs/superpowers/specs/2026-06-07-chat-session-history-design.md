# 对话保存与新对话功能设计

日期：2026-06-07

## 目标

为“智能体伴学”和“课堂讨论”增加可见的对话管理能力，让用户可以开启新对话、保存当前对话、查看历史对话，并从历史对话继续学习。

本功能不覆盖资料、动画实验室、C 语言编译器等工具页面，避免把非对话型操作混入聊天历史，保持界面简洁。

## 用户体验

在“智能体伴学”和“课堂讨论”页面的主聊天区域顶部增加两个轻量入口：

- 新对话：保存当前内容后开启一轮空白对话。
- 历史对话：打开一个抽屉或弹层，展示已保存的对话列表。

历史列表中的每条记录只展示核心信息：

- 自动标题：优先使用第一条用户问题生成，例如“链表头插法理解”。
- 类型标签：智能体伴学或课堂讨论。
- 更新时间：用于快速定位最近学习记录。

点击历史记录后恢复该对话。恢复后用户可以继续提问，系统会在同一条历史对话中继续保存。

## 数据范围

智能体伴学会保存：

- 所属章节或场景。
- 消息列表。
- 更新时间。
- 自动标题。

课堂讨论会保存：

- 消息列表。
- 当前讨论模式。
- 已选择的老师和学生角色。
- 当前是否正在等待用户回答。
- 待回答问题、选项和互动记录。
- 更新时间和自动标题。

## 存储策略

登录用户使用服务器数据库保存，支持跨设备恢复。

未登录用户使用浏览器本地存储，限制保存数量，避免本地数据无限增长。未登录状态下界面提示“登录后可云端同步”。

现有后端已经有按场景保存对话的 `conversations` 表和 `/api/conversations` 接口，但它只能保存每个场景的一份草稿。新功能需要在兼容旧数据的基础上增加“多条会话”能力。

## 推荐架构

新增独立的会话数据结构，避免破坏现有按场景草稿逻辑。

每条会话包含：

- `id`：唯一会话 ID。
- `type`：`coach` 或 `classroom`。
- `scenario`：当前章节或学习场景。
- `title`：自动生成或后续可编辑的标题。
- `messages`：消息列表。
- `classroomState`：课堂讨论专用状态，可为空。
- `createdAt`：创建时间。
- `updatedAt`：更新时间。

前端状态增加：

- `chatThreads`：所有历史对话。
- `activeCoachThreadId`：当前智能体伴学会话。
- `activeClassroomThreadId`：当前课堂讨论会话。

后端增加多会话接口：

- `GET /api/chat-threads`
- `POST /api/chat-threads`
- `PUT /api/chat-threads/:id`
- `DELETE /api/chat-threads/:id`

旧接口 `/api/conversations` 暂时保留，作为兼容层，不在本次迭代中删除。

## 界面原则

界面必须保持轻量，不增加固定大侧栏，不把历史记录堆在主页面。

推荐使用右侧抽屉或小弹层展示历史对话。抽屉打开时显示列表，关闭后页面仍保持当前简洁布局。

按钮文案保持短：

- 新对话
- 历史
- 继续
- 删除

删除历史对话需要二次确认，避免误删。

## 错误处理

云端保存失败时，不阻断用户继续聊天，先保存到本地，并用轻提示说明“网络异常，已暂存在本地”。

登录失效时，不清空当前对话，提示重新登录后再同步。

恢复历史对话失败时，保留当前页面状态，提示用户稍后重试。

## 测试重点

需要验证：

- 智能体伴学可以新建对话、保存旧对话、恢复历史对话。
- 课堂讨论恢复后能保留角色、模式、等待回答状态。
- 登录用户刷新页面后历史仍存在。
- 未登录用户刷新页面后本地历史仍存在。
- 删除一条历史不会影响其他历史。
- 旧的 `/api/conversations` 行为不被破坏。

## 不做事项

本次不做全站行为记录。

本次不做复杂文件夹、标签、搜索和批量管理。

本次不做对话分享链接。

本次不强制用户手动点击“保存”，以自动保存为主，减少学习中断。
